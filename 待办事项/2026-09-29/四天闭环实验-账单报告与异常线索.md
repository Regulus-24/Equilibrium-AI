# 四天闭环实验：有依据的账单报告与异常线索

> 2026-09-29后续调整：用户要求最近一周不接API，并结合账单分析与理财操作。本周以《一周离线闭环-账单到理财.md》为准；本文模型接入/对照/预算安排暂缓，保留为后续实验参考，不自动执行。

设计日期：2026-09-29。实验编号：HZ-EXP-01。
状态：仅方案。尚未建立测试集、开发流水线、接入模型、运行实验或创建后台自动化；以下阈值为拟定验收标准，不是已测成绩。四天为依赖满足后的工作批次，不承诺连续四个自然日必定交付。

## 1. 目标与可证伪的问题

在相同账本与证据条件下，相比现有统计摘要，模型报告能否帮助用户更准确地理解主要变化，定位需要核实的记录，并采取具体核查动作，同时不制造数字、原因或欺诈判断？

本轮限定月报、两类线索：金额偏离个人同类历史；疑似重复记录。年度报告复用后续展开。基金跟踪、产品推荐、订阅识别、写账本/锁卡与美化不纳入本实验。用已有记账和月度统计作为基础，不以训练模型为前置。

## 2. 三个版本与归因

- A：现有统计加固定事实摘要，无模型，作为业务基线。
- B0：相同数字证据和同一异常候选集合，加DeepSeek结构化解释，作为首次AI基线。
- B1/B2：在开发集失败上改进提示词、证据选择或检测参数后的候选，单轮只变更一类因素。

A与B的异常候选完全相同，模型收益只评价解释与使用效果。检测器版本另比较候选精确率/召回率，不能把规则筛选成绩说成AI识别提升。真实模型与离线模拟运行明确分开；没有API只能完成离线管线，不能宣布AI有效。

## 3. 数据集：先有可核对答案，再写生成器

建立60份合成账本任务，每份固定as_of、当前月、历史记录、预期事实、可核实线索、不能下的结论。数据不读写日常data/ledger.json；日期固定保证跨天可复现。

| 场景族 | 数量 | 应覆盖 |
|---|---:|---|
| 正常与变化 | 12 | 多类别增减抵消、新类别、一次性大额、正常高额、无明显线索 |
| 异常候选与相似反例 | 12 | 金额偏离、疑似重复、同额不同用途、正常固定金额、已注明原因的大额 |
| 信息不足 | 12 | 空账本、缺上月、少量同类样本、备注含糊、不能区分重复记账/真实两次支付 |
| 时间及金额边界 | 12 | 本月未结束、跨年、闰月、零基数、分币精度、修改/恢复快照 |
| 输入及运行故障 | 12 | 备注中的伪指令、异常文本、越权要求、超时、格式错误、陈旧报告 |

每族分6份开发、3份验证、3份最终留出，共30/15/15。按原始账本生成模板和场景变体成组分配，不能只随机换日期金额就跨集合泄漏。冻结manifest及hash，原始真实答案只给评估器，不给报告模型。

“答案”分三类：精确金额/日期/证据ID；根据可见信息应提示的核查项；不能判断的事项。同样的可见账单不能因编写者秘密设定了“其实是盗刷”就被标为模型应该识别的欺诈。含糊案例允许多种合格表述，不以固定措辞为标准答案。

开发前人工复核至少10份代表案例，数值答案采用手算小样本和独立参考计算交叉检查，不直接调用待测monthly_comparisons生成自己的全部答案。数据生成后若标签有歧义先修订并重新冻结，不边调模型边改标签。

变形检查：打乱记录顺序金额应不变；金额按倍数缩放占比不变；加入无关备注不改变数值；同一快照重复调用不变；修改记录后旧报告必须失效。不是额外模型任务数，先作为本地确定性检查。

## 4. 流水线与接口草案

输入账本快照 → 计算证据 → 检测候选 → 生成报告 → 校验 → 评分 → 失败分类 → 提出单点改进 → 回放对比 → 保留或丢弃候选。

建议新增独立实验目录，具体文件名实施时确定：

```text
experiments/bill-analysis/
  config.json                 # 预算、阈值、模型参数和版本
  datasets/{dev,val,holdout}/  # 冻结样本，生成阶段后不改
  prompts/                    # 提示词版本
  runs/<run_id>/              # 输入hash、结构化输出、指标、失败清单
  decisions/                  # 每次候选选择/拒绝的理由与证据
```

证据包：snapshot_id、as_of、两期起止日期及天数、已记录数据提示、统计指标及metric_id、entry_id、候选类型/基线数量/阈值/相关记录、缺数据标志。所有金额使用整数分；本月至今对上月整月，完整月对完整上月，不自动改用户口径。

报告结构：period、key_changes、review_items、limitations、next_questions。每个事实引用metric_id或entry_id，解释区分fact/hypothesis/question。优先由程序渲染金额和日期，模型选择引用并组织解释，不让自由文本成为数字事实的唯一载体。

检测器v0建议：
- 疑似重复：同日、同金额、同类别且备注接近的记录组，去重输出一个核查项；不认定为重复银行扣款。
- 金额偏离：同类别个人历史中位数/稳健离散程度与最小绝对差额联合判断。阈值仅在开发集选择，样本量门槛先设为可配置的实验参数；MAD为0、历史稀疏需单独处理，不能除零或自动判异常。
- 将检测器称为统计/规则候选模块。语义能力首先通过有证据的解释、信息缺口判断和核查问题验证。

校验器：schema、引用存在、记录属于期间、金额与指标一致、快照未变、零基数及缺期处理、工具允许范围。自由文本原因是否有依据不能靠schema证明，需人工审阅；第二个LLM的评语只能辅助定位问题，不能充当真值。

非法结果标为invalid并隔离，不向用户呈现为成功报告；可返回明确标为确定性统计的降级结果。日志保留原始失败，重试成功也不能抹掉首次失败率。

## 5. 验收标准（实验启动前冻结）

| 项目 | 初版门槛 | 计算/说明 |
|---|---|---|
| 确定性证据 | 全部案例金额、期间、ID正确 | 精确数值按整数分比较；百分比按既定精度；关键错误不取平均掩盖 |
| 发布报告硬错误 | 0个 | 错金额、错期间、假引用、写操作、缺数据硬下结论均阻止发布；自由文本需抽检，不能声称自动验证语义完全正确 |
| 模型正常任务有效率 | ≥90% | 非故意故障案例中，经最多1次修复后有效的报告数/任务数；另报首次有效率与重试数，不能靠拒绝全部报告达到零错 |
| 故障处理 | 注入故障场景全部按预期失败/降级 | 不把预期超时拒绝计入正常任务成功率，也不宣称降级为AI成功 |
| 异常候选精确率 | ≥80% | TP/(TP+FP)，记录原始计数；匹配“类型+记录ID集合”，重复提示不重复记TP |
| 异常候选召回率 | ≥80% | TP/(TP+FN)，只以可观测、可核实候选为分母；对可判断的正例弃答计FN |
| 正常场景打扰 | ≤20%案例出现无根据核查项 | 单独报告，避免大量正常记录稀释误报；含糊案例依事先约定标签评分 |
| 信息不足处理 | 对应案例100%说明限制 | 必须指出缺什么，不能仅给泛化免责声明 |
| 人工实用性 | 10组成对案例中B至少7组获偏好或独立任务表现更好 | 打乱A/B位置；问主要变化是什么、查哪笔、为什么、下一步做什么；事实/引用错误另作否决项，不靠文采得分抵消 |
| 稳定性 | 最终留出集独立生成3次，逐次达硬门槛及有效率要求 | 不挑最好一次；记录模型/参数/时间，不能保证提供商完全确定性 |

异常指标须分别报告两种类型及合计。若某一集合正例/预测数不足10，相关百分比只作探索性数据，不能宣布可靠性达标；补充全新冻结案例后再评价。分母为0显示N/A，不能记100%。

人工审阅建议由用户/顾梓洋核对依据，胡芷澄评价是否理解与能完成任务，按实际可用时间安排；至少一位不参与本轮提示词修改的人独立审阅。只有开发者自评时报告为初步内部结果。外部用户未参加就不能声称需求或落地得到验证。

## 6. 自我改进机制：有边界的候选实验

每轮保存失败类别：计算、候选误报/漏报、证据遗漏、引用错误、无依据推断、缺数据不承认、格式、超时、可读性。

1. 优先处理硬错误，再处理开发集出现频率最高的问题；列出失败案例与假设。
2. 每天最多2个候选，每个只改提示词、证据选择、检测参数中的一种。使用预先允许的配置变体，自动化可选择/回放；模型新提出的任意代码补丁只作为建议，由正常开发与代码检查处理。
3. 修复依据仅限开发集；每个候选先回放开发集与已知回归，保存与现行版本的逐例差异。
4. 每天最多1个候选进入验证集，改进应体现为目标失败减少，硬错误无新增，关键指标无倒退；若出现取舍则保留原版、记录问题供人工决定。
5. 最终留出集仅在候选冻结后运行；只看最终验收，不用其答案改提示词。失败则如实记录；一旦用于修复就转为开发数据，下一次须另建留出集。
6. 自动选择只更新实验目录的候选指针。接入日常Demo前执行已有行为回归及相关浏览器检查，人工报告审阅达标；无自动覆盖日常账本或发布部署。

严禁通过删失败题、放宽阈值、修改正确答案、只挑成功输出提高成绩。确需修正错误标签，记录原因、版本及影响，重新跑受影响基线，不能与旧分数直接比较。

## 7. 四个工作批次

| 批次 | 执行任务 | 可检查交付 |
|---|---|---|
| 第1天 | 冻结60任务、标注与参考答案；接证据包和A；建立运行目录及评分器 | 离线单命令回放结果、已复核样例、数据manifest；与现有统计一致性通过 |
| 第2天 | 检测器v0；接真实DeepSeek、结构化报告和校验；建立B0 | 首次真实模型run、完整成功/失败计数、日志和成本；缺密钥时停在offline-ready |
| 第3天 | 按开发集最多两次单点改进；验证集选择；安排成对人工评价 | B0/B1差异、失败减少/回归表、人工原始反馈；不达标则保留B0或A |
| 第4天 | 冻结候选，最终留出集三次运行；核查硬错误/覆盖/异常与人工结果；达到门槛才集成报告入口 | 通过/未通过/样本不足的明确结论，运行复现说明、已知限制、下一轮任务 |

任一批次依赖缺失不跳过验收。日程是范围建议，实际工时尚未核实；未过门槛即延后，不以赶天数改指标。年报与基金研究在本闭环形成后复用资料/证据/评测机制。

## 8. 自动运行与资源上限

实施入口拟支持离线/在线、数据分组、候选版本、最大调用数；不是已有命令。调度层和流水线分开：可先手动启动同一命令，后续定时只负责触发它；主机须开机、运行环境及网络就绪。

本方案未创建日程。实施后建议开发阶段每天一次完整批次，有变更时跑受影响开发案例；最终留出不进入每日任务。无新输入/候选时直接跳过，不重复烧API。仅完成、关键失败或需要人工判断时通知。

建议上限（未授权支出、待启动时配置）：每天150次模型请求、整个实验450次；所有报告/修复/改进建议调用和重试均计入。另设总token上限与人民币预算，人民币额度未填写则在线模式拒绝启动；所选模型当时官方费率进入配置，不能用猜测价格估算。请求预留最大输出token及剩余额度，遇到预算不足提前停止。

请求超时建议60秒；最多一次重试，指数退避且遵守服务端限制；正常输出修复也计入总尝试/预算。连续3次基础设施错误触发熔断，凭证错误立即停；每天改进候选耗尽则停。单轮总时长建议上限30分钟，可断点恢复；请求同一任务不并发重复提交。缓存实验版本与输入hash完全一致的开发结果；稳定性验收禁用生成缓存。

需要的前置：服务端环境变量提供API密钥（不放聊天或仓库）、选定模型及预算、独立合成数据目录、人工审阅人可用时间。缺API可完成第一批次和模拟响应的故障测试，但在线效果验收必须等待真实调用。

## 9. 每轮产物与失败后的动作

run_manifest.json：代码/提示词/检测器/数据hash、模型与参数、as_of、开始结束时间、运行模式。
metrics.json：各项分子/分母、首轮及重试有效率、分类型异常指标、耗时、token/费用、未运行项。
failures.jsonl：case_id、失败类别、依据、期望、实际、重试、候选修复及是否复现。
reports/：结构化报告、渲染报告、校验结果；仅合成内容，不记录密钥。
decision.md：选用/拒绝哪个候选、为什么、哪些证据、人工意见、待解决问题。

连续两轮无提升：停止盲目改提示词，检查数据是否足够、标签是否可观测、当前字段是否能解决任务；有缺字段再提出最小补充方案。精确度高但用户无偏好：保留统计基线，重新核实报告任务而非包装更漂亮。检测达标、解释不达标：可单独保留待核实候选，不能称智能报告通过。失败记录本身也是本轮产出。
