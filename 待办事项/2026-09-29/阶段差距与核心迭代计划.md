# 衡智：阶段差距与核心迭代计划

整理日期：2026-09-29。状态：方案与任务计划，不是完成声明；本轮不改Demo代码。

## 本轮安排依据

用户明确：最近几周优先内核实现、功能实用性、真实应用落地；外观设计与PPT集中到最后两周。每周继续维护可运行版本、测试结果、原始反馈与事实记录，不要求每周制作PPT、宣传稿或精剪展示视频。影响操作的可读性和交互缺陷随时修复。

三场景仍为账单分析、理财操作、卡片管理；年轻上班族仍是待验证的目标人群。单银行、人民币、本机研究原型与合成数据边界不变。真实需求可以现在验证，真实银行接入不作为未经授权的默认实施目标。

最后两周暂按作品提交节点倒排，具体锚点待用户确认；提交日期和官方要求待核实。以下按三个核心迭代安排，每个原则上约一周，但不是工时承诺。三人可投入时间尚未确认；进度不足时缩范围，不并行承诺所有功能。

## 最近几周的开发主线

### 第一迭代：可核对的AI账单问答

用户任务：用自己的话问“这个月比上月多花在哪里”，得到正确期间、金额、分类变化及可打开的依据。

- 先固化工具：期间收支查询、分类查询、月度比较、按记录ID查看依据。复用现有计算，模型不自行重新加总。
- 建立单一只读助手，先覆盖结构化期间/分类/差额问答；“生日送朋友的东西”等用途语义检索单独评测，不声称已覆盖。
- 期间有歧义时澄清；用户指定的比较规则必须保留：本月至今对上月整月，不自动改成同期。
- 回答携带期间、账本版本、来源记录或汇总证据；模型只使用工具返回的数据。对无法核实的原因明确未知。
- 服务端限制工具名、参数、调用次数和可返回记录；首版无写工具。请求失败、模型超时、无数据均有可理解的降级结果。
- 记录模型/配置版本、请求耗时、工具成功与失败、调用量；密钥不进前端/仓库，日志不记录凭证。模型候选、运行方式和调用预算在接入前明确，本计划不绑定厂商或假定已有可用API。
- 若模型暂不可用，先完成同一工具契约与回放测试；仍需明确“尚未实现真实模型调用”，不得以模板冒充AI。

交付物：可运行只读问答、固定评测集、失败清单、一次独立操作记录。工具层和评测层即便换模型也保留。

### 第二迭代：一个能被用户确认或纠正的识别功能

依据第一轮访谈选订阅候选或异常线索之一。默认建议先订阅候选，因为“这几笔是否同一项重复扣费”便于逐笔核对；这是待验证选择，不是已证实需求。

- 若选订阅：设计可选商户/服务字段，验证同服务多次扣费、周期与金额变化；保留原备注和旧数据兼容。历史不足只提示不足。
- 将相似记录组成候选，展示日期、金额、识别依据。用户能确认订阅或排除，并保存纠正结果；排除后的候选不反复打扰。
- 覆盖房租、分期、重复手动录入、一次性购买等容易误判情形。重复扣费不直接等于订阅，更不代表欺诈。
- 如外部反馈更需要异常核对，则先做一种明确线索（例如疑似重复记账），不要泛称交易反欺诈；同样有依据、确认和排除。
- 记录候选数、正确数、误报、漏检和人工核对时间；同时记录“没有检测到”的案例。合成测试与用户测试分开。

交付物：一个实际候选识别模块、确认/排除状态、离线案例集和外部反馈。暂不做取消订阅、扣款或自动金融操作。

### 第三迭代：在三个场景间打通一条有用流程

主线A：账单问答 → 用户明确用款需求 → 条件比较 → 展示保留/排除依据。

- 把用款日期、可承受损失、流动性需求和资料缺口结构化；明确账本结余不能直接当可投资金额。
- 小量合成产品补齐期限、到账假设、风险及条件来源；不捏造收益或把“未排除”说成“适合购买”。
- 对测评缺失、条件冲突、无合适产品给出明确结果。真实资料引用和专业审阅另留记录，不做正式适当性结论。

主线B仅在有明确关联时开展：选中有模拟卡标识的记录 → 查看卡片 → 预览锁卡 → 用户确认 → 执行及核验。

- 手动账本目前没有银行账户关联，不得把任意记录默认关联到0428；需要明确模拟数据标识或用户选择。
- LLM只能解释或请求预览，确认由用户操作，服务器验证；自然语言“知道了”不得直接替代确认。
- 保留过期、状态变化、重复提交与重启恢复测试。没有消费授权模拟就不声称锁卡后消费已被阻断。
- 沙箱申购/赎回属于更后续的门槛项，先核实赛题要求和资源再决定；只在独立模拟环境中设计，未接入真实银行。

交付物：至少一条三场景中相关能力组成的真实可操作流程；理财/卡片模块各保留明确能力边界，不能只留展示页面。

## 用户与应用验证：从第一迭代开始

建议目标为先联系3—5位符合定位的潜在参与者，争取2—3次独立试用；这是招募目标，不是已存在的用户数，也不代表统计意义上的市场验证。

1. 问最近一次查看账单的任务、现有方式、频次和困难；先听事实，再展示功能，避免只问“你会不会用”。
2. 邀请自愿参与者在本机用虚构或自拟不含敏感信息的样例完成任务，不索取银行凭证、完整流水。可讨论其真实经历而不收集真实账单。
3. 比较原有页面查找和新问答的完成结果、耗时、求助次数、错误理解；同一题先做会有学习效应，应换等价题或交换次序并记录局限。
4. 隔几天询问是否愿意再次使用、哪个环节有帮助或无用；没有后续使用也记录，不挑选好评。
5. 为每条问题记录原话摘要、场景、角色、是否目标人群、是否内部成员、对应改动和验证结果；不给未发生的反馈填结果。

真实落地近期指在真实需求下由真实参与者验证原型价值。银行内嵌、正式试点、真实API连接是另外的层级，须有接口方与权限等条件后再开展；官方资源核实和潜在对接可以现在推进。

## 验收门槛与观察指标

以下是建议的首轮门槛，不是当前成绩。验收样本和门槛在运行前固定，失败不能靠删除题目解决。

| 对象 | 建议验收方式 |
|---|---|
| 确定性计算 | 已有回归全部通过；新计算用事先写好的期望值检查，必须正确 |
| AI问答 | 初始40题：15普通查询、8含糊表达、7缺数据、5日期/金额边界、5备注指令干扰；保存原始结果和判定依据 |
| AI核心约束 | 测试中所有涉及金额/期间/证据的答案正确，越权写入为0；不满足则继续修复，不称可靠 |
| AI任务完成 | 首轮建议至少36/40符合预先标注的正确答案或应澄清/应拒答行为；说明失败类型，不只报总分 |
| 延迟与资源 | 分别记录模型耗时和工具耗时，重复测量后报告中位数及尾部表现、错误和调用成本；在确定运行设备及模型后设数值目标 |
| 候选识别 | 同时报精确率、召回率、分母及误报案例；门槛依据用户容忍程度确定，不预设虚假的通用准确率 |
| 外部实用性 | 记录独立完成、耗时、求助与复用意愿；人数小就以案例与局限呈现，不宣称市场验证完成 |
| 数据与操作 | 旧账本兼容、迁移前备份、测试目录隔离；工具与权限服务端检查；模拟/真实字段可辨认 |

## 控制范围与退出条件

- 每轮一个主要功能，最多一条并行的用户验证工作；先把已选功能做到可用，不把所有待办一起启动。
- 没有可信样本时，不做训练效果承诺；预训练/通用微调学习放其他窗口。
- 语义检索、年度对比、纪念日提醒、全格式账单导入、云账号和多设备云同步不成为第一轮前置条件。
- 若手动录入被目标用户反复证实是主要障碍，再提议单一格式导入；不因“功能还缺”自动开启全平台适配。
- 最后两周以已有可用内核为基础集中审美、交互统一、手工PPT、演示材料和答辩演练；持续修阻塞缺陷，原则上不再引入新的大业务模块。
- 期间不足三个核心迭代时，优先只读账单问答、目标用户反馈、现有理财/卡片的正确联动；缩减识别范围与新交易动作。最后两周起点以用户明确锚点和官方时间为准。
